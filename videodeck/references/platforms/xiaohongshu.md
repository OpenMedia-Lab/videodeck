# Xiaohongshu

Use current [xhs-cli](https://github.com/OpenMedia-Lab/xhs-cli) help and its
video-publishing contract. Inspect supported upload, processing, dry-run,
publication, readback and edit operations; a new-video publisher does not imply
support for replacing an existing video's media.

## Platform version before confirmation

Read current [official community rules](https://agree.xiaohongshu.com/h5/terms/ZXXY20221213003/-1)
and any actual account moderation notice. Check the served document's revision
date; a page retrieved today is not necessarily a newly issued policy.
Review the complete body, cover, onscreen text, subtitles and narration together.
External URLs and invitations to another platform can be classified as outbound
guidance even when they point to the author's own technical article. Keep complete
source URLs and research provenance in the local delivery. For the platform
version, use neutral author/work-title attribution where appropriate and remove
outbound calls and contact routes. Split links, QR codes, search hints and vague
invitations can retain the same outbound intent; evaluate them against the actual
notice rather than assuming that less explicit wording is approved. Treat source titles and project names
as technical context rather than automatically deleting every third-party name.

If approved narration contains an outbound call, identify its exact segment and
resolve the allowed audio change. Preserve the accepted voice and technical
explanation; review the changed complete film and matching captions. A body-only
fix leaves an onscreen URL or spoken invitation unchanged.

Follow the [full metadata confirmation](../publishing.md) for each changed version,
including native topic entities, visible topic markers, activity, visibility and
any native content declaration. Do not infer permission to delete, repost, appeal
or change public copy from an earlier approval of different content.

## Submission and recovery

Keep reusable material receipts and a unique durable publication journal. A lost
response requires reconciliation against creator state, not a new receipt and
another POST. Verify the submitted video and independent cover, real body line
breaks, native topics, activity relation, visibility and requested declaration.
File IDs can become canonical IDs; use the CLI's original-media fingerprint
verification and retain its evidence, rather than editing the original payload
until IDs match. Report explicit body-format normalization separately from exact
text equality.

Read creator moderation state in addition to public-feed availability. In an
observed restriction, `my-notes` exposed punishment/advice fields even though
creator detail remained enabled/public and the note was readable. A successful
upload, readable note or activity binding does not establish recommendation
eligibility, effective task count or rewards.

For a restricted existing note, inspect the actual reason and supported in-place
edit path. Prepare concrete replacement media/copy for review before mutation.
Prefer preserving the note ID when the platform supports the required edit.
If it cannot replace the video, explain that limit and obtain the user's choice
before deletion or another public post. Editing a violation does not itself prove
that a recommendation restriction has been lifted; read back the later observed
status and report any remaining uncertainty.
